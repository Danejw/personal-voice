# 05 — Continue with the right conversation context

Branch `shared-memory-assistant` at committed `3267903` (version 0.3.9). Phases 02, 03, and 04 are still uncommitted in this tree. This phase does not start phase 06. None of the three migrations was applied to a production project.

Starting a saved thread is meant to give a new Assistant session the earlier conversation, once. A follow-up on another device has not been checked against the live model. The context builder and the seed-once path are in tests. The phase is not accepted until the device script at the bottom is actually run and a model follow-up is recorded.

## What changed

- `src/assistant/contextRestore.ts` builds the text for a new session from the saved rows. The last 8 messages stay verbatim, up to 6,000 characters. Older messages become one summary of at most 2,000 characters. The whole seed stays at most 8,000 characters. Those are character counts of the seeded text, not model tokens. The Live session still uses its own sliding window after the seed.
- A stored summary is used only when `summary_through_seq` is the last older message and `summary_fingerprint` matches those rows. A deleted or edited prefix drops the stored body and rebuilds from the rows that remain. The same fingerprint is not written again. A different fingerprint must name the fingerprint it replaces.
- Tool rows are seeded as text: "Already finished: {name}. {outcome} Do not run this again." The seed has no `functionCall` and no `toolResponse`. Interrupted lines stay one unfinished turn. Live partials are not stored and are not summarized.
- `supabase/migrations/20260930220000_assistant_context.sql` adds `summary_body`, `summary_through_seq`, `summary_fingerprint`, and `context_items` on `assistant_conversations`. `save_assistant_summary` rejects a prefix that does not end at the named sequence (`ASSISTANT_SUMMARY_STALE`) and a competing fingerprint that does not name the stored one (`ASSISTANT_SUMMARY_CONFLICT`). `save_assistant_context_items` stores notes, one selection, one handoff, and screenshot metadata. A screenshot body must be empty. `delete_assistant_conversation` also clears the summary and the attachment list.
- `AssistantConversationStore` builds that seed after a successful claim, before a fresh Start. It saves a new summary when one was built. A conflict re-reads the winner. A failed summary save still starts from the recent messages and says so. Attached notes, the selection, and the handoff are saved with their id, text, source, and capture time. A screenshot row stores the source and time and no pixels.
- `AssistantController` sends that seed with the existing `assistantHistorySeed` (`clientContent`, `turnComplete: false`) on the first ready of a socket opened without a resumption handle. A socket opened with a handle does not receive the seed again. The seed is not added to the visible transcript.
- The conversation bar says starting sends the saved conversation as earlier context and does not run old actions again. A stale or failed summary and an unavailable screenshot are named on that bar.
- `docs/SPEC.md` and `docs/ARCHITECTURE.md` now say a later Start seeds the saved transcript once, and a resumed socket does not receive it again.

Dictation, notes, handoffs, settings, local device preferences, and `usage_epoch` protection are unchanged. Microphone audio is still not stored. The model stays `gemini-3.8-live` on the constrained v1alpha socket.

## Decisions

- The summary is built on the device from the saved rows. There is no second Gemini call, so the tests do not depend on the model. The watermark is the last covered sequence plus a fingerprint of those rows. A newer message does not invalidate a summary of the older prefix.
- Same fingerprint is a no-op on the server (`saved: false`). A different fingerprint must pass `p_replaces` equal to the stored fingerprint. The loser re-reads. If the winner still matches the rows, that body is used. Otherwise the screen says another summary was saved and the recent messages are still included.
- Screenshot pixels are out of this phase. The seed says the image is not available and is not this device's current screen. A screenshot still held on this device is omitted from the seed because the existing snapshot path still sends that JPEG once per connection.
- A finished tool is stored as a `tool` row, hidden from the transcript, and explained in the seed. It is not sent back as a tool call. An action that already finished while the lease was lost is recorded locally and is not sent to the model as success.
- An empty thread sends no seed. If the saved messages cannot be read, Start does not open the microphone. The offline text cache is not given to the model.
- Setup is still rebuilt on every connection, so platform tools and permissions are the current device's. The last seeded line says this device's screen and permissions are what they are now.
- Official Live API reference (`https://ai.google.dev/api/live`, fetched 2026-09-30) still describes `clientContent.turns` as conversation history and `turnComplete: false` as waiting instead of starting a reply. Video remains `realtimeInput.video`, separate from that text history. The same page documents `historyConfig.initialHistoryInClientContent`, which holds history until `turnComplete` is true. This phase did not switch to that flag. The working seed already uses `turnComplete: false`, and the model and endpoint were left as they are.

## Deployment

Apply all three files, in order, on a project you have confirmed. Do not guess the ref.

1. `supabase/migrations/20260930200000_assistant_conversations.sql`
2. `supabase/migrations/20260930210000_assistant_lease.sql`
3. `supabase/migrations/20260930220000_assistant_context.sql`

Until the third file is applied, Start can still claim a lease from the second file. Saving a summary or an attachment then fails in the background. The screen says the summary or the notes could not be saved, and the recent messages are still used for that session. They will not be on the next device until the save succeeds.

Rollback of this context file only, keeping conversation rows: drop `save_assistant_summary`, `save_assistant_context_items`, and `assistant_context_items`. Drop `summary_body`, `summary_through_seq`, `summary_fingerprint`, and `context_items`, or leave the columns unused. Recreate `delete_assistant_conversation` from the phase 04 lease file if that replace must be undone. The lease and the conversation tables stay.

## Device script

NOT RUN. Do not mark any step passed until it is done on one Android phone and one Windows install, both on the same account, after all three migrations are on the project you mean to use. A live model answer is part of step 2. The automated tests do not stand in for that answer.

1. On the phone, open Assistant, decide something specific (for example, meet on Friday), and press End. On Windows, open the same thread and press Start. Ask a follow-up that only makes sense if Friday was the decision. The answer should use that saved context. The phone's old actions should not run again.
2. A long thread should still start. The seeded text stays within the character budget above. The model smoke result for that follow-up is recorded here only after it is actually heard.
3. Delete or correct a line, then start again. The removed words should not come back through an older summary. The bar should say the saved summary was out of date when that happens.
4. A thread that had a screenshot should say the image is not available and is not the current screen. Windows should not treat yesterday's desktop as its own screen.
5. End the session, let it resume from a `GoAway` if one occurs, and confirm the transcript was not sent a second time. A brand-new Start sends it once.

## What works now

A new session can be given the saved conversation once, with older lines folded into a watermarked summary and finished tools described as already done. A resumed socket skips that seed. Deleted text is not copied back out of a stale summary. Screenshot pixels are not stored, and the screen says the image is missing. Two real devices have not been checked, and the live model has not been asked the follow-up.
