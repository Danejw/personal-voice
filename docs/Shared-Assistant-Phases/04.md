# 04 — One conversation, one answering device

Branch `shared-memory-assistant` at committed `3267903` (version 0.3.9). Phases 02 and 03 are still uncommitted in this tree. This phase does not start phase 05. Neither migration was applied to a production project.

The phone, laptop, and desktop are meant to show the same saved Assistant threads. Only one of them answers at a time. That live check was not run on devices. The code and the automated races are in. The phase is not accepted on hardware until the script at the bottom is actually run.

## What changed

- `supabase/migrations/20260930210000_assistant_lease.sql` adds `claim_assistant_conversation` and `release_assistant_conversation`. It replaces `append_assistant_message` with the same ten arguments plus `p_fence bigint default null`, so an older call that omits the fence still parses. Assistant and tool rows must carry the current fence and the holding device. A user row does not. A retry of a message id that is already stored with the same content succeeds after the fence moves. Both tables get `replica identity full`. If the database has the `supabase_realtime` publication, the migration adds both tables to it. A local Postgres without that publication still applies.
- `AssistantConversationStore` claims a 45-second lease and renews it every 20 seconds while this device is producing. Renewing on the same device does not move the fence. Continue here takes the lease and moves the fence. Opening a thread does not start the microphone.
- A realtime event, coming back to the app, or the network returning only schedules a re-read of the saved rows. The event payload is not the history. While this device is live and still holds the lease, that re-read does not replace the transcript on screen.
- A generated line that loses the lease is kept on this device under `assistant.recovery.v1.<userId>` and is not written into the shared thread. The user's own line stays in the pending queue and can still be saved. The screen says "Not shared. Another device continued." Dismiss removes that local line.
- The last readable copy is `assistant.cache.v1.<userId>` (up to 30 threads, 80 turns each, text only). If the list cannot be loaded, that copy is shown with a note that Assistant needs a connection. A delete removes the thread from the cache. Switching accounts reads only the new account's keys.
- The header Start button claims the lease and then starts. If another device holds the lease, the button says Continue here. End still ends the session and releases the lease when this device still holds it. A second device can view without the microphone turning on.
- New tool work does not start when this device is not the producer. An action that already finished is not undone and is not run again. Auto-run versus review is unchanged.
- `PV_ASSISTANT_CONTINUATION_V1` may include `conversationId`. The receiver opens that saved thread and does not start the microphone. A package without that field still parses, and that older path still starts a new session. An unknown key is still rejected.
- `docs/SPEC.md` and `docs/ARCHITECTURE.md` now describe the single producer. They still say a later Start does not send the saved transcript to the model.

Dictation, notes, handoffs, settings, local device preferences, and `usage_epoch` protection are unchanged. Microphone audio is still not stored.

## Decisions

- The lease lasts 45 seconds. The holder renews at 20 seconds. The server accepts 15 to 120 seconds. Taking the conversation from anyone else, including an expired holder or an empty lease, adds one to the fence. The same device renewing does not.
- Realtime is a hint. Subscribe, a missed event, a reconnect, and background/resume all end in the same re-read, ordered by `seq`. Duplicate ids collapse to one turn.
- User text can be saved after the lease is lost, because that is what the person said. Assistant and tool text cannot. After `ASSISTANT_LEASE_LOST`, this device stops the live session, parks the generated line, and does not merge it into the other device's answer.
- A message that the server already stored can be retried safely. The matching id returns before the lease is checked.
- Continue here is the only new way the microphone turns on for a shared thread. `AssistantController.start()` itself is not blocked, so an older continuation package still starts the way its test expects. The Start button on the Assistant page goes through the claim first.
- The active-device line uses the name from the account's device list. An unknown id is "another device."
- Offline Gemini is not offered. The cache is text for reading. After the lease expires, this device does not keep generating shared work.
- Account, pending, open thread, cache, and recovery are all keyed by the signed-in user. The lease is memory on that store, not a global pointer.

## Deployment

Apply both files, in order, on a project you have confirmed. Do not guess the ref.

1. `supabase/migrations/20260930200000_assistant_conversations.sql`
2. `supabase/migrations/20260930210000_assistant_lease.sql`

Hosted Supabase already has `supabase_realtime`, so the second file adds the two conversation tables to that publication. After it runs, Start claims a lease. Until it runs, Start shows a save error and does not open the microphone.

Rollback of this lease file only, keeping conversation rows: drop `claim_assistant_conversation` and `release_assistant_conversation`, drop the eleven-argument `append_assistant_message`, and recreate the ten-argument function from the phase 02 migration. Then revoke execute on the dropped functions if they remain. Rolling back both phases is the phase 02 rollback, which drops the conversation tables.

## Device script

NOT RUN. Do not mark any step passed until it is done on one Android phone and two Windows installs, all on the same account, after both migrations are on the project you mean to use.

1. On Windows A, open Assistant, speak one sentence, and press End. On Windows B and the phone, open Assistant. The sentence should appear. Their microphones should stay off. The page should say the conversation is active on A's device and that this device is only viewing.
2. On Windows B, press Continue here. B's microphone should start. A should stop answering. If A still had a reply in flight, A should show "Not shared. Another device continued." That reply should not become B's answer.
3. Send the phone to the background. On B, add another line. Bring the phone forward. The new line should show up. Turning B's network off after a line has saved, then reopening, should still show the saved copy and say Assistant needs a connection. It should not promise a live answer.
4. On A, delete the thread while B is offline. Reconnect B. The thread should stay gone.
5. Sign B out and into a different account. B should not show A's threads, the parked reply, or A's lease.

## What works now

The saved thread can be claimed, watched, and taken over in tests. A late answer is kept on the device that lost, and the words the person said can still be saved. The model still does not receive the saved transcript when Assistant starts. That is phase 05. Two real devices have not been checked.
