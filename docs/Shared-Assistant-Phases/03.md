# 03 — Save and reopen Assistant conversations

Branch `shared-memory-assistant` at committed `3267903` (version 0.3.9), with the uncommitted phase 02 storage work still in the tree. This phase does not start phase 04. The migration from phase 02 was not applied to a production project.

## What changed

- The Assistant screen saves finalized user and assistant turns through `assistantConversationsApi` and reopens the last thread for that account.
- `AssistantController` reports each committed turn once. End, a refused connection, barge-in, and a reconnect keep unfinished speech as `interrupted` instead of dropping it. Streaming text stays in `liveUser` and `liveText` until that boundary.
- `AssistantConversationStore` owns the list, the pending queue, and the open-thread pointer. `ConversationBar` is the compact list: New, open, rename, delete, and Saving / Saved / Retry.
- Account-scoped local keys are `assistant.pending.v1.<userId>` and `assistant.open.v1.<userId>` on the existing key-value storage. There is no queue service.
- Sign-out still ends the live session first, then switches the store, so the last line is filed on the account that spoke it.
- Continue on another device still parses `PV_ASSISTANT_CONTINUATION_V1`. That path now opens a new conversation id before seeding, so the copy is not appended onto the previous thread.
- `docs/SPEC.md` and `docs/ARCHITECTURE.md` now say the screen saves the transcript and that a later Start does not send it to the model.

No new migration. No lease is acquired. Dictation, notes, handoffs, settings, and device preferences are unchanged.

## Decisions

- A finished user line (typed send or a final input transcript) and a `turnComplete` reply are stored as `final`. The in-memory turn omits `status` in that case. Assistant speech that stops before `turnComplete` is `interrupted`: End, the user talking over a reply, a server `interrupted` event, a reconnect, or Stop and listen. A user line that is still only a partial when End is pressed or the connection fails is also `interrupted`.
- Message ids are the turn ids assigned before the write. Create and append are the phase 02 idempotent RPCs, so a crash after the server commit and before the local ack retries the same id and does not add a second row.
- The pending item records the account and conversation at the moment the turn is committed. A later account switch updates the old account's queue when that write finishes. It does not paint that text onto the new screen. Opening another thread bumps a generation so a slow load cannot replace the thread you just opened.
- Delete removes that conversation's queued writes and, if an append is already in flight, deletes the thread again after that append returns. The tombstone from phase 02 still blocks a retry from recreating the id.
- The list is one page of 50 conversations. The last opened id is per account on this install, not one global pointer.
- The first user line becomes the title when the title is still "New conversation". Rename of a thread that is not on the server yet is kept for the create call.
- Citations that are not https, or that have no title, are left off the saved message so one bad citation cannot reject the line. Tool arguments are not stored.
- Starting Assistant on a saved thread shows the transcript and opens a new Gemini session without that history. Restoring model context is phase 05. The existing continuation handoff still sends its own bounded copy once, because that path already did.

## What works now

On this device, a signed-in Assistant thread can be created, spoken or typed, ended, and opened again with the same message ids, including a line that was cut off. Saving, saved, and retry are visible on the Assistant page. Switching accounts or threads during a slow write does not file that line on the wrong thread. Deleting a thread drops its unsaved queue. The model does not yet remember the saved transcript when you press Start again. Another device still does not share the live thread; that lease is phase 04.
