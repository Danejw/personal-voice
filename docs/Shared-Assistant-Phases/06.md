# 06 — Remember preferences across separate conversations

Branch `shared-memory-assistant` at committed `3267903` (version 0.3.9). Phases 02 through 05 are still uncommitted in this tree. This phase does not start phase 07. None of the migrations was applied to a production project.

An explicit preference is meant to follow the account onto a new conversation on another device. That live check was not run. The memory rules, the screen, and the session restart are in tests. The phase is not accepted until the script at the bottom is actually run.

## What changed

- `supabase/migrations/20260930230000_assistant_memories.sql` adds `assistant_memories`. One active row per account and key. A correction marks the previous row superseded and inserts the next revision. Forget marks the active row forgotten and leaves it. `remember_assistant_memory`, `forget_assistant_memory`, and `list_assistant_memories` require the signed-in user. `assistant_memory_suppressed` is true when that key was forgotten from that source conversation.
- `src/assistant/memory.ts` is the rule set: key and value limits, explicit over extracted, revision conflict, suppression, and the text a session may hear. At most 8 active memories and 2,000 characters. Forgotten rows are absent. The fingerprint changes when an included value or revision changes.
- The Assistant page has a Remembered disclosure: key, value, why it is there, Edit, and Forget. Example: key `answer_length`, value `Prefer short answers.`
- Voice tools `list_memories`, `remember_memory`, `change_memory`, and `forget_memory` use the same rules. Remember, change, and forget wait for the usual confirmation. List does not.
- A new session receives the active list once, as a context note, separate from analytics personal context and from the saved transcript. A resumed socket with the same list does not receive it again. If the list changes after this session already heard it, the socket restarts without the resumption handle. The screen says the session is restarting so it does not keep the old preference. Deleting the row is not described as the live model forgetting it.
- A failed refresh can show the last saved copy on the device. That copy is not sent to the model.
- `docs/SPEC.md` and `docs/ARCHITECTURE.md` now say explicit memories are account data, separate from the analytics profile and from deleting a conversation.

Dictation, notes, handoffs, settings, local device preferences, and `usage_epoch` protection are unchanged. Microphone audio is still not stored. The model stays `gemini-3.8-live`. There is no automatic learning and no backfill in this phase.

## Decisions

- Scope is `account` only. Device settings stay on the device. Analytics personal context stays a separate note.
- The stable identity is the key, such as `answer_length`. "Answer length" and `answer_length` are the same key. Each correction is a new row. The previous row becomes superseded. Two writers must send the revision they read. The first match wins. The second gets `ASSISTANT_MEMORY_CONFLICT` and the list is read again.
- An explicit remember replaces an extracted guess at that key. A second remember of an explicit key is refused; change is the way to correct it. This phase never writes `origin = 'extracted'`. The column allows it so a later phase can store a guess without a new table.
- Forget does not delete the conversation, and deleting a conversation does not forget the memory. The source conversation id stays on the forgotten row. `assistant_memory_suppressed` stays true for that pair, so a later guess from the same conversation stays blocked. A later explicit Remember is allowed and does not delete the forgotten row. The saved transcript can still contain the words. Forget is not Delete.
- The live socket cannot drop a fact it already heard. After a change or forget that the session already received, this device closes that socket and opens a new one without the resume handle. The new session hears only the current active list. A resume whose list has not changed does not send the note again.
- Offline, the screen may show `assistant.memory.v1.<userId>`. The model hears only a list the server confirmed in this process.

## Examples

- "Remember that I prefer short answers." Tool `remember_memory` with key `answer_length`, kind `preference`, value `Prefer short answers.`
- "Change that preference." Tool `change_memory` with the same key and the new value. The revision just read has to match.
- "Forget that." Tool `forget_memory` with that key. The conversation it came from stays. A new session does not hear it.

## Device script

NOT RUN. Do not mark any step passed until it is done on one Android phone and one Windows install, both on the same account, after all four migrations are on the project you mean to use.

1. On the phone, open Remembered and save key `answer_length`, value `Prefer short answers.` End Assistant if it is running. On Windows, open a new Assistant conversation and ask for a long explanation of something small. The answer should stay short because of that preference. The phone's old conversation does not have to be open.
2. On Windows, edit the value to `Prefer detailed answers.` If Assistant was already in that session, it should restart and say it is not keeping the old preference. A follow-up should follow the edited value, not the old one.
3. Forget `answer_length` on Windows. Start Assistant again on the phone. It should not apply the short-answer preference. The forgotten row should still be listed as forgotten after both apps are restarted. The conversation where it was taught should still open and show its text.
4. Sign Windows into a different account. It should not show the first account's memories.
5. On two devices, edit the same key from the same revision. One save should win. The other should say another device changed that preference, and the list should show the winner.

## What works now

The account can be taught a preference, shown it, corrected, and told to forget it. A new session is given only the active memories that fit, and a live session restarts when that list changes so a forgotten fact is not left in the open connection. Two devices have not been checked, and the live model has not been asked to follow one.
