# 02 — Durable conversation storage

Branch `shared-memory-assistant` at `32679034d1f3004f4a996cd3f193abf513cb16df` (version 0.3.9). That is not the reference commit `8c3835a`. There was no `docs/Shared-Assistant-Phases/01.md`. ## Decisions

- Account ownership is `auth.uid()` inside security-definer functions with `search_path = ''`. Every public function also requires `p_user_id` to equal that account. Another account's conversation id returns not-found. A mismatched `p_user_id` returns forbidden.
- Message ids are client UUIDs. The same id and the same content is a no-op. The same id with different content fails and does not add a row. Sequence numbers are assigned under a conversation lock, so concurrent appends get 1..n with no gaps.
- Partials are not rows. Status is `final` or `interrupted`. Citations are `url` and `title` only, https, at most eight. A tool row stores `tool_name` and `tool_outcome` text. There is no column for audio, tokens, resumption handles, or tool arguments.
- Delete blanks the title, deletes messages in the same transaction, clears the lease fields, and increments `fence` once. The id row remains, so create and append of that id fail. A second delete succeeds and does not move `fence` again. Message text is not kept for a retention window. The id stub is what stops a retry from recreating the thread.
- `lease_device_id`, `lease_expires_at`, and `fence` are reserved for phase 04. This phase does not grant a way to acquire the lease. Authenticated clients can select live rows only. Insert, update, and delete on the tables are revoked.
- Authenticated list and append RPCs are the service path. Direct table writes are rejected.

## Deployment

Do not run this against a project until its ref is confirmed.

Apply `supabase/migrations/20260930200000_assistant_conversations.sql` after the existing migrations. Then regenerate `src/types/database.ts` from that project and replace the hand-written assistant section if the generator output differs.

Rollback that keeps every existing table, and also keeps any conversation rows already stored: revoke `execute` on the seven `public.*assistant*` functions granted to `authenticated`. Old clients never called them.

Rollback that removes saved conversations and leaves every older table in place:

```sql
drop function if exists public.list_assistant_messages(uuid, uuid, bigint, integer);
drop function if exists public.list_assistant_conversations(uuid, integer, timestamptz, uuid);
drop function if exists public.get_assistant_conversation(uuid, uuid);
drop function if exists public.append_assistant_message(uuid, uuid, uuid, text, text, text, uuid, jsonb, text, text);
drop function if exists public.delete_assistant_conversation(uuid, uuid);
drop function if exists public.rename_assistant_conversation(uuid, uuid, text);
drop function if exists public.create_assistant_conversation(uuid, uuid, text);
drop function if exists public.assistant_message_matches(public.assistant_messages, uuid, text, text, text, uuid, jsonb, text, text);
drop function if exists public.assistant_fetch_conversation(uuid, uuid, boolean);
drop function if exists public.assistant_lock(uuid, uuid);
drop function if exists public.assistant_citations(jsonb);
drop function if exists public.assistant_title(text);
drop function if exists public.assistant_require_account(uuid);
drop function if exists public.assistant_message_owner();
drop table if exists public.assistant_messages;
drop table if exists public.assistant_conversations;
```

## What works now

The database can store an account's Assistant threads and the final or interrupted lines in them, and the app has a typed service for that. Ending a conversation on screen still does not write those rows. Opening Assistant on another device still does not show a saved list. Dictation, notes, handoffs, and settings behave as before.

Phase 03 can call `assistantConversationsApi` to save and reopen a thread. Phase 04 still has to enforce the lease before two devices can speak for the same thread.
